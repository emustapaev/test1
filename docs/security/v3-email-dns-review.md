## 4. DNS-генератор (`scripts/dns/render-table.mjs`) и Zoho

| # | Проверка | Статус | Комментарий |
|---|---|---|---|
| 4.1 | Нет MX/TXT на apex | ✅ | Генератор завершается ошибкой (проверено тестами). |
| 4.2 | Нет `_dmarc` из outputs | ✅ | Отказ; опциональная `_dmarc` добавляется только если в baseline её нет. |
| 4.3 | DKIM SES не пересекается с Zoho | ⚠️ | Проверка работает только по селекторам, найденным в baseline. Публично селектор Zoho не найден (#85), поэтому проверка фактически не защищает. Токены SES — случайные 32 символа, коллизия практически невозможна. Рекомендация: узнать селектор в Zoho Admin и перезапустить `snapshot.sh`. |
| 4.4 | MAIL FROM на поддомене | ✅ | `mail.krunai.uz` (MX + SPF) — apex SPF Zoho не затрагивается. |
| 4.5 | Типы записей | ⚠️ | Генератор не ограничивает типы: CNAME на `www`/`mail`/`_domainkey` проходят, а, например, CNAME на `_dmarc` или apex-ALIAS — только `_dmarc` отсекается. Рекомендация (не критично): добавить белый список типов/имён. |
| 4.6 | DMARC `p=none` и spoofing | ⚠️ | `p=none` только мониторинг: подделанные письма от `@krunai.uz` не блокируются. Рекомендации: (1) добавить `rua=mailto:...` для отчётов; (2) после 2–4 недель отчётов убедиться, что Zoho и SES проходят DKIM-выравнивание; (3) перейти на `p=quarantine` (затем `reject`, `pct` поэтапно). DMARC опирается на DKIM: SPF SES на `mail.` не выравнивается с From (ADR 0004). Если DMARC у клиента уже есть — не менять без согласования. |
| 4.7 | Отправитель `noreply@` | ⚠️ | Подделка `noreply@krunai.uz` третьей стороной возможна, пока DMARC `p=none`; других ящиков-получателей у домена это не затрагивает. |

## 5. Итог

Критичных проблем нет. Исправлено: ужесточена валидация email (п. 2.3). Остаточные риски (⚠️) — организационные или некритичные, вынесены в рекомендации:

1. Выяснить селектор DKIM Zoho и пересобрать baseline (п. 4.3).
2. Спланировать ужесточение DMARC (п. 4.6).
3. При появлении CI-деплоя — выдать роли права только на SES identity `krunai.uz` (п. 1.5).
4. `ALLOWED_ORIGIN` содержит два origin через запятую и возвращается как есть в `Access-Control-Allow-Origin`; браузеры такое значение отвергают. Функционально не критично (запросы идут same-origin через CloudFront `/api/*`), но это стоит исправить отдельным тикетом: возвращать origin запроса, если он в списке.
5. Неизвестные поля в теле запроса (п. 2.6).
6. X-Forwarded-For берётся из заголовка запроса (первый элемент), клиент может подделывать его для обхода rate limit; относится к модели угроз #57.
